# P05 · Auditoria imutável, leitura auditada e máscara de documentos

Data: 25/09/2026 (relatório escrito na integração da trilha de banco)
Branch e commits: `claude/kraamzorg-delivery-review-6kzd8q`. `0005_auditoria.sql` e `supabase/tests/005_auditoria.sql` entraram no commit de segurança `b123584`.

## Feito

1. **Chave do HMAC no Vault** (`auditoria_hmac`): gerada dentro do banco
   com 32 bytes aleatórios só quando ainda não existe; nunca passa por
   arquivo, migration ou variável de ambiente.
2. **Colunas sensíveis** em `privado.auditoria_coluna_sensivel`: a lista
   mínima do PRD 13 [v4.2] mais os acréscimos desta sessão (ADR 0002,
   seção 7).
3. **`privado.auditar()`** em toda tabela de negócio de `public` e `agente`
   (menos `log_auditoria`, `fila_sincronizacao`, `mensagem`,
   `evento_familia` e o schema `agente_n8n`): grava as colunas alteradas,
   `auth.uid()`, a origem de `app.origem` e o ip da requisição; coluna
   sensível vira `"[oculto]"` mais HMAC-SHA256 com a chave do Vault. Sem a
   chave, a escrita auditada é recusada.
4. **`log_auditoria` imutável**: `update`, `delete` e `truncate` revogados e
   recusados por gatilho, inclusive para `service_role` e o dono. Única
   exceção: `privado.anonimizar_ip_log_auditoria`, que só troca o `ip` e só
   roda dentro da retenção (P20, O-06).
5. **Leitura do log** só pela diretoria, por função (`api.log_auditoria`, no
   P07, em AAL2 e registrando a própria leitura).
6. **Leitura auditada**: `privado.registrar_leitura()` e o exemplo
   `assistencial.ler_acompanhamento(familia_id)` (`volatile`), que grava
   `leitura` no log antes de devolver.
7. **`privado.mascarar_documentos(texto)`**: CPF com dígitos verificadores
   válidos, cartão pelo Luhn (juntando grupos separados por espaço, ponto,
   hífen ou barra; 4-6-5 do Amex), fora do formato de telefone, e validade e
   CVV na mesma mensagem de um cartão ocultado. É a definição de referência
   que o n8n copia (PRD 19.5).
8. Teste `005_auditoria.sql` (89 asserções): o aceite inteiro do P05 v2,
   inclusive os 16 casos da máscara, o log de `pessoa.nome`,
   `handoff.resumo` e `familia.estado_sensivel_motivo` sem o texto original,
   e o HMAC do CPF diferente de `sha256(cpf)` e igual ao HMAC com a chave do
   Vault.

## Decisões tomadas nesta sessão

- Acréscimos à lista de colunas sensíveis, pela leitura mais segura:
  `bebe.sexo`, `oportunidade.motivo_perda_detalhe`, `ocorrencia.titulo`,
  `relatorio_medico.destinatarios`, `pos_venda.pesquisa_token_hash`,
  `conversa.wa_jid` e `wa_lid`, `perfil` (nome, email, telefone_e164),
  `profissional` (nome, telefone_e164), `tarefa` (titulo, payload),
  `notificacao` (titulo, corpo), `automacao_execucao.payload` e
  `contrato.formulario_token_hash`. Mudar a lista é migration nova.
- A chave do HMAC é gerada pela migration quando falta. Na integração,
  `supabase/LIGAR.md` passou a recomendar criar a chave antes do primeiro
  envio, com o valor do cofre, para existir uma cópia fora do banco; a
  migration encontra a chave e não faz nada.
- Trocar a chave é decisão de runbook, porque os HMACs antigos deixam de
  ser comparáveis.

## Como testar

Sem Docker (esta máquina), na raiz do repositório:

```bash
cd supabase/sem-docker
PGPORT=54342 PGDATA=/tmp/kz-pg-final scripts/iniciar.sh    # sobe o Postgres 16 local (idempotente)
PGPORT=54342 PGDATA=/tmp/kz-pg-final scripts/testar.sh     # reset do zero + seeds do config.toml + pg_prove
PGPORT=54342 PGDATA=/tmp/kz-pg-final scripts/parar.sh
cd ../..
node supabase/checar-seed.mjs
```

Um arquivo só, depois de um `scripts/resetar.sh` (o `000_harness.sql` cria o
schema `testes` que os outros usam):

```bash
sudo -u postgres pg_prove --host 127.0.0.1 --port 54342 --dbname kraamzorg --username postgres \
  supabase/tests/000_harness.sql supabase/tests/ARQUIVO.sql
```

Com Docker (prova final antes de qualquer `db push`, `supabase/LIGAR.md`):

```bash
supabase start
supabase db reset     # migrations + [db.seed] de supabase/config.toml
supabase test db
```
