   `sem_acento` e da fronteira de privilégio.
4. **Integração (25/09)**: `supabase/config.toml` mínimo e sem segredo

## Ficou de fora (e por quê)

- `supabase init`, `supabase start`, `db reset` e `test db` com Docker: a
  máquina não tem Docker. O `config.toml` foi escrito à mão no formato da
  CLI; a prova final continua sendo a do Docker (`supabase/LIGAR.md`, passo 2).
- Job `supabase test db` da CI: continua `if: false` em
  `.github/workflows/ci.yml`. Ligar pede a action da CLI e Docker no runner;
  fica para a próxima sessão que puder rodar a CI.
- `docs/runbooks/ambientes.md`: o conteúdo (o que só se configura no painel,
  sessão de 8 horas, MFA, backups) está em `supabase/LIGAR.md`, passo 4. O
  P14 decide se move para `docs/runbooks/`.
- `src/lib/db/` (cliente de servidor, cliente de serviço com `server-only`,
  `pnpm db:types`): feito pela sessão de app do P07
  (`docs/sessoes/P07-app.md`). Os tipos foram regenerados contra o banco
  final nesta integração (`pnpm db:types:local`).

## Decisões tomadas nesta sessão

- A revogação do `execute` de `PUBLIC` é global
  (`alter default privileges revoke execute on functions from public`, sem
  `in schema`): a forma por
  schema não fica gravada quando o resultado é igual ao padrão do Postgres,
  e a função nova voltaria a nascer executável por todos (verificado na
  prática, comentário na migration).
- `pg_net` e Vault são stubs locais, documentados no README do sem-docker.
  O Vault local guarda texto puro: nunca pôr segredo de verdade ali.
- `config.toml`: `major_version = 17` (conferir com o projeto remoto no
  `link`); senha com no mínimo 12 caracteres, com minúscula, maiúscula e
  número [confirmar: Leonardo]; cadastro público desligado, porque a conta
  nasce do convite da diretoria.
- Os seeds ficam em `[db.seed]` do `config.toml`, a mesma lista para
  `supabase db reset` e para o sem-docker, sem copiar a base de
  conhecimento para dentro do `seed.sql`.

## Como testar

Sem Docker (esta máquina), na raiz do repositório:

```bash
cd supabase/sem-docker
PGPORT=54342 PGDATA=/tmp/kz-pg-final scripts/iniciar.sh    # sobe o Postgres 16 local (idempotente)
PGPORT=54342 PGDATA=/tmp/kz-pg-final scripts/testar.sh     # reset do zero + seeds do config.toml + pg_prove
PGPORT=54342 PGDATA=/tmp/kz-pg-final scripts/parar.sh
cd ../..
node supabase/checar-seed.mjs
```

Um arquivo só, depois de um `scripts/resetar.sh` (o `000_harness.sql` cria o
schema `testes` que os outros usam):

```bash
sudo -u postgres pg_prove --host 127.0.0.1 --port 54342 --dbname kraamzorg --username postgres \
  supabase/tests/000_harness.sql supabase/tests/ARQUIVO.sql
```

Com Docker (prova final antes de qualquer `db push`, `supabase/LIGAR.md`):

```bash
supabase start
supabase db reset     # migrations + [db.seed] de supabase/config.toml
supabase test db
```
